# 小天才 IM 协议：从零复现的完整推导

本文把「不看客户端源码、只靠抓包和试探」把 IM 通道跑通的全过程整理成可复现的推导。
目标是让任何人按本文能独立重写一个客户端，并且知道**哪些参数必须从客户端取、为什么取不到就要不到**。

文中所有真实 ID / 手机号 / 票据均已替换为占位符。

---

## 1. 架构总览

整条链路有两段完全独立的服务：

```
┌─────────────┐   ① SSO（HTTPS，443）      ┌──────────────────┐
│  我们的程序  │ ──────────────────────────> │ account.okii.com │  账密换票据
└─────────────┘                             └──────────────────┘
       │
       │ ② IM（TLS，8002）
       ▼
┌──────────────────┐
│ im3.okii.com     │  用票据登录，收发消息
└──────────────────┘
```

关键认知：**两段是独立的**。

- SSO 负责「你是谁」，产出 `accountToken`（票据）
- IM 负责「收发消息」，只认票据 + 设备身份

这也是为什么「SSO 签票成功」不等于「IM 能用」——本文第 8 节会证明这个差别是致命的。

## 2. 传输层

```
主机        im3.okii.com
端口        8002
协议        TLS 1.3（标准证书，**无证书固定**，所以可以中间人抓包）
```

标准 TLS 且没有 pinning，这是整条链路能被逆向的前提。

## 3. 字节编码

### 3.1 varint（LEB128，小端续位）

```
值 0x04        -> 04
值 0x8D 0x71   -> 低7位 | 0x80, 再 高7位   （长度、tag 都用它）
```

实现见 `src/xtc_qq_bridge/im/session.py` 的 `enc_varint` / `dec_varint`。

### 3.2 TLV

```
tag(varint) | length(varint) | value(length 字节)
```

整数一律**大端裸字节**，不用 varint。这一条踩过坑，见 7.2。

---

## 4. 两种帧格式

同一个连接上有两种魔数，**结构不同**，别混：

### 4.1 公钥交换帧（0x36 / 0x37）

```
magic(1B) | length(varint) | payload(TLV...)        ← 没有 cmd 字节
```

请求（实测 6 字节）：

```
36 04 01 02 03 e8
│  │  └─┬─┘ └──┬──┘
│  │    │      └── tag1, len2, value 0x03e8 (RID=1000)
│  │    └───────── tag1, len2
│  └────────────── varint 长度 4
└───────────────── 魔数 0x36
```

响应（实测 416 字节）：

```
37 9d 03 01 02 03 e8 02 ...
│  └─┬─┘
│    └── varint 长度 413
└─────── 魔数 0x37
```

其中 `tag10` = 266 字节 PEM 公钥（RSA-1024）。

### 4.2 业务帧（0xA0）

```
magic(1B) | cmd(1B) | length(varint) | payload
```

`cmd` 是业务命令号，见第 6 节。

## 5. 握手

### 5.1 取公钥

发 `0x36`，收 `0x37`，从 `tag10` 取出 PEM 公钥。

### 5.2 会话密钥协商（cmd 33）

```
payload = tag1(RID)                      # 1002
        | tag11( RSA_PKCS1_v1_5(SESSION_KEY) )
        | tag10( b"\x01" )
```

**`SESSION_KEY` 必须是 16 个可打印 ASCII 字符。**

这是最容易踩的坑：服务端把它当 **String** 处理，非 ASCII 字节会被替换成 U+FFFD（`EF BF BD`），
两边密钥不一致，后续所有帧都解不开。

实测可用值：`0123456789abcdef`。

协商成功返回 `code=200`。

### 5.3 载荷加密

对 `tag10` 的内容做**循环异或**：

```
cipher[i] = plain[i] ^ key[i % 16]
```

推导验证（真实抓包）：

```
明文字节 [0] = 0x23   (tag35)
密文字节 [0] = 0x13
0x13 ^ 0x23 = 0x30   而 key[0] = 0x30   ✓
```

## 6. 命令号一览

| cmd | 名称 | 用途 |
|---|---|---|
| 7 | Heartbeat | 心跳保活 |
| 12 | Sync | 拉消息（增量） |
| 32 | EncryptSet 包装 | 注册/登录都发在 cmd32 里 |
| 33 | EncryptSet | 会话密钥协商 |
| 34 | — | 协商应答 |
| 40 | SingleMessage | 发一条消息 |

`cmd32` 的载荷再包一层 `tag10`（加密），解出来后**还有一层内层头**：

```
inner_cmd(varint) | inner_len(varint) | inner_payload(TLV...)
```

内层 `inner_cmd` 用于区分注册（`tag33`）与登录（`tag35`）。

**这一层如果不剥，会以为"什么都没解析出来"**——实测最初就卡在这里。

## 7. 注册与登录

### 7.1 注册（cmd32 → 内层 tag33）

内层字段（实测 14 个）：

| tag | 值 | 说明 |
|---|---|---|
| 1 | RID | 请求号 |
| 25 | 票据 | SSO 签发的 `accountToken` |
| 11 | appKey | App 常量 |
| 22 | Android 构建号 | `TQ3A.230901.001` |
| **24** | **手表 ID** | **必须是本账号绑定的那块手表** |
| 13 | deviceId | IM 设备身份 |
| 26 | 版本号 | 例如 94605 |
| 20 | 设备型号 | `Subsystem for Android(TM)` |
| 12 | 包名 | `com.xtc.watch` |
| 10 | 1 | 固定 |
| 23 | 7 字节常量 | |
| 14 | 33 | 固定 |
| 15 | 系统描述 | |
| 16 | 12595 | 固定 |

响应 `code=200` 时，`tag10` 是 `registId`。

**`tag24` 填错（例如沿用别的账号的手表 ID）会得到 `102400`。**

### 7.2 登录（cmd32 → 内层 tag35）

内层字段（实测 9 个，共 382 字节）：

| tag | 长度 | 说明 |
|---|---|---|
| 1 | 2 | RID |
| **24** | 301 | BRP JSON（见下） |
| 26 | 32 | deviceId 字符串 |
| 18 | 7 | `16094875454681141` |
| 20 | 1 | 平台 1 |
| 10 | 4 | registId |
| 11 | 4 | **`"null"` 字面量** |
| **12** | **4** | 版本号 |
| 21 | 8 | 毫秒时间戳 |

整帧（含外层 tag10 与 tag35）= **678 字节**，与 App 完全等长。

#### BRP JSON（tag24 的内容）

```json
{"accountId":"<手表 ID>","appId":"0","deviceId":"<BRP设备ID>","imFlag":"1",
 "mac":"<32位hex>","machineId":"<32位hex>","program":"android",
 "registId":<数字>,"timestamp":"YYYY-MM-DD HH:MM:SS","token":"<票据>"}
```

`timestamp` 必须是**当前时间**。

#### 「一个字节」的坑

`tag12`（版本号 94605）最少只需 3 字节，但 **App 恒定用 4 字节**。
服务端按 4 字节整型解析，少一个字节整帧错位：

| | App | 修复前 | 修复后 |
|---|---|---|---|
| tag12 长度 | 4 | 3 | 4 |
| 帧总长 | 678 | 677 | 678 |

### 7.3 帧里没有校验字段

逐字节比对确认：**帧内没有任何 HMAC / checksum / 签名字段**。
完整性由 TLS + 会话密钥加密保证，服务端不会因为"内容被改过"而拒绝。

推论：只要加密正确、字段对齐，服务端就看不出是我们发的。

## 8. 决定性实验：票据 + 设备身份

这是整个逆向里最关键的一节。

### 8.1 SSO 对任何 deviceId 都发票

| 使用的 deviceId | SSO 返回 |
|---|---|
| App 用过的那个 | `000001` + 票据（deviceId 回显） |
| **全新随机 32 位 hex** | **`000001` + 票据（同样回显）** |

也就是说 SSO **不校验** deviceId 是否真实存在。

### 8.2 但 IM 只认「绑定过的」deviceId

同样的两个 deviceId，同样的其它参数，只做注册：

| deviceId | IM 注册结果 |
|---|---|
| **App 用过的那个** | **`200`** |
| **全新随机** | **`102400`** |

### 8.3 结论

```
im_sso_device_id 必须是 IM 服务端已经绑定到该账号的设备身份。
绑定动作只发生在「真实客户端首次连 IM」时。
→ 无法推导，只能观测一次。
```

用随机 deviceId 会得到「SSO 发票成功 + IM 拒绝」这种极具误导性的组合状态，
排查时极容易误判成签名或报文问题。

## 9. 同步（cmd 12）

### 9.1 请求

| tag | 含义 |
|---|---|
| 1 | RID |
| 11 | **本账号 imAccountId** |
| 12 | registId |
| 13 | syncKey（游标） |
| 14 | pageSize |

`tag11` 必须是本账号自己的 imAccountId。填 0、填 registId 都返回 `102400`。

### 9.2 应答是多帧的

一条消息一帧。**只读第一帧会丢掉后面所有消息**——这是"收不到消息"的早期原因之一。

### 9.3 syncKey 语义

`syncKey` 是**增量游标，不是历史页码**：

| 操作 | 结果 |
|---|---|
| 传 0 | 从当前缓冲区开始，返回全部待收消息 |
| 传返回的新游标 | 只返回更新的 |
| 往回翻 | 永远空（服务端不保留完整归档） |

游标位置随帧型不同：

- **消息帧**：`tag15`
- **纯 ack 帧**（无 `tag14`）：`tag13`

### 9.4 消息类型（tag18）

| type | 含义 |
|---|---|
| 3 | 聊天消息（文字 / 表情 / 图片都走这个） |
| 24007 / 27 | 电量 |
| 1001 | 已读回执 |
| 43002 | 健康数据 |
| 35 / 5 | 成员信息 |
| 20013 | 会话 id |

### 9.5 消息体格式

> **表情包和图片也是 `type=3`**，和纯文字同一种帧。

外层是标准 8 字段 JSON：

```json
{"content":"...","hintType":-1,"isSensitive":false,"msgNewContent":"",
 "msgNewType":0,"showType":0,"text":"...","textMsgType":0}
```

`content` 又是一段 JSON 字符串。文字消息里它就是文本本身；媒体消息里它长这样：

```json
{"appPath":"http://.../emoji/<code>","code":"<code>","emojiType":1,
 "facecode":"...","packageName":"...","seriesId":"..."}
```

判据：

- 带 `emojiType` / `facecode` / `packageName` / `seriesId` → **表情包**
- 只有 `url` / `imgUrl` 之类 → **图片**

只取 `text` 会把这类消息当文字发出去（QQ 收到一段 JSON），这就是"表情包没转发"的原因。

### 9.6 时间戳

消息原始发送时间是 **`tag17`**（毫秒）。

但**表情包/图片帧偶尔不带 tag17**，此时必须按 `17 → 19 → 21 → 15` 依次找候选值，
并且只接受像时间戳的值（≥1e12 当毫秒；1e9~1e10 当秒并补成毫秒）。

找不到时**不要退回"当前时间"**——那会让滞留消息看起来是刚发的。

## 11. 心跳（cmd 7）

```
tag1(RID) | tag2(秒级时间戳)
```

应答 7 字节，**没有状态码字段**——只能靠"有没有收到数据"判断连接是否存活。

作用：票据会过期，但**会话一旦建立就不会因票据过期而失效**。
心跳不断就能长期保活，从而绕开"定期重新登录"。

> ⚠️ 心跳线程与轮询线程共用同一条 TLS 连接时，**必须整体加锁**。
> 并发 `recv`/`send` 会让 OpenSSL 的 BIO 状态错乱，实测直接导致进程 SEGV。

## 12. SSO 流程

### 12.1 端点

```
POST /app/rsakey     明文表单: appId, sign, mac, timestamp
POST /app/loginV3    加密体: 用上一步的公钥加密 AES 密钥
```

**不是 `/app/loginV2`。** 客户端常量表里同时有 `login2` 和 `loginV3`，没有 `loginV2`——
早期凭直觉用了 `loginV2`，签出的票 IM 一律不认。

### 12.2 `loginV3` 的请求参数（中间人解出）

```json
{"nDeviceId":"<32 hex>","userName":"<手机号>","areaCode":"86","password":"...",
 "appId":"11","sign":"<md5>","days":"-1",
 "deviceId":"<32 hex>","mac":"<32 hex，与 deviceId 同值>",
 "timestamp":"YYYY-MM-DD HH:MM:SS"}
```

两个容易漏的点：

- **`nDeviceId`** 是 App 额外带的字段。固定复用同一个值；每次换新值等于伪装成另一台设备。
- **`mac` 与 `deviceId` 同值**，且必须是 32 位十六进制。

### 12.3 签名

```
sign = lowercase_hex( MD5( url + "##".join("k=v" 按 key 排序) + secret ) )
```

### 12.4 换设备验证

新设备首次登录返回：

```json
{"code":"010410","desc":"换设备登录，需要验证账号",
 "data":"{\"checkTypes\":[3,4,6,1,2],\"checkCode\":\"...\",\"endTime\":...}"}
```

必须人工完成短信/手表验证。验证通过后该 deviceId 才成为「已知设备」。

## 13. 参数分类（换账号时谁要重取）

| 类别 | 字段 | 换账号 |
|---|---|---|
| **App 常量** | `im_app_key`、`im_sdk_version`、`im_sdk_version_name`、`im_platform`、`im_program`、`im_app_id`、`im_im_flag` | ❌ 通用，永不改 |
| **设备级** | `im_device_id_tlv`、`im_device_id_brp`、`im_mac`、`im_machine_id` | ❌ 描述跑客户端的机器，可沿用 |
| **账号级** | `mobile_id`、`im_sender_account_id`、`im_regist_id`、`im_account_token`、`im_sso_device_id` | ✅ 每账号一套 |

### 13.1 三个「必须从客户端取一次」的参数

| 参数 | 含义 | 能否推导 |
|---|---|---|
| `im_sso_device_id` | 账绑的 IM 设备身份 | ❌ 见第 8 节 |
| `mobile_id` | 账号绑定的手表 ID（32 位小写字母数字，形如 `<prefix>…`） | ❌ 服务端生成 |
| `im_sender_account_id` | 手机侧 imAccountId | ❌ 服务端分配 |

实测过 `tag11=0` / `tag11=registId` 做同步探测，都返回 `102400`，
**没有"用票据换 imAccountId"的公开路径**。

服务端生成的标识有共享前缀（同一账号下多个设备 ID 开头一段完全相同），
说明它们是服务端按规则生成后下发的，不是本地哈希——这也排除了"从设备指纹算出来"的可能。

### 13.2 取到之后就不需要客户端了

```
票据会过期 → 但可以用 SSO 账密重签（纯 HTTPS，不需要 root、不需要 App）
```

`tools/im_account.py login` 一行命令即可续票 + 自检。

## 14. 复现检查清单

按顺序验证，任一步失败就不要往下走：

1. TLS 连得上 `im3.okii.com:8002`
2. `0x36` → `0x37` 能拿到 PEM
3. `cmd33` 会话密钥协商 → `code=200`
4. 能解开 `tag10`（循环异或正确 → 内层头可读）
5. 注册 `code=200` 且拿到 registId
6. 登录 `code=200` 且帧长 678 字节
7. 同步 `code=200` 且能解析出 `type=3` 消息
8. 发送 `code=200`

第 5 步失败（`102400`）基本都是三个客户端参数之一不对，优先怀疑 `mobile_id` 和 `im_sso_device_id`。

## 15. 踩坑速查

| 现象 | 根因 |
|---|---|
| 所有帧都解不开 | `SESSION_KEY` 含非 ASCII，被服务端替换成 U+FFFD |
| 解析不到任何字段 | 没剥内层 `[cmd][len]` 头 |
| 只收到第一条消息 | 只读了第一帧，应答是多帧的 |
| 登录 `102400` | `mobile_id` 不是本账号的手表 ID |
| 登录 `4200` | 票据过期，或 `deviceId` 不是绑定的那个 |
| 表情包只发出"图片"两字 | 媒体消息也是 `type=3`，需解析 `content` 里的 JSON |
| 滞留消息时间显示成拉取时刻 | 缺 `tag17` 时退回了 `now()` |
| 进程随机 SEGV | 心跳与轮询并发读写同一 TLS 连接 |
